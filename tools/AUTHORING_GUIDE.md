# CISA 문제은행 작성 가이드 (Question Authoring Guide)

이 문서는 문제은행을 **일관된 실전 품질**로 작성·보강하기 위한 규칙이다.
초기 4,000문항뿐 아니라 이후 추가되는 모든 문제 팩에 동일하게 적용한다.
기준: ISACA CISA 2024 Job Practice (D1 18% · D2 18% · D3 12% · D4 26% · D5 26%), CRM 28판.

---

## 0. 실전 기준 v2 — 아래 모든 장보다 우선 적용

근거: ISACA 출제 지침 — 보기는 정답 1 + 오답 3, 오답은 “해당 분야를 잘 모르는 응시자가 고를 만큼 그럴듯해야” 하며, 4개 보기는 문장 구조·길이가 비슷해야 한다. NOT·EXCEPT·LEAST는 출제하지 않는다.
실제 시험의 난이도는 지엽 지식이 아니라 **모두 그럴듯한 보기 중 ISACA 관점의 최선·우선순위를 고르는 판단**에서 나온다.

1. **4개 보기 모두 실무상 정당한 선택지**: 같은 범주(모두 감사 절차 / 모두 통제 / 모두 위험 / 모두 개념). 각 오답은 *다른 상황이었다면 정답이 될 수 있는* 실제 조치·개념이어야 한다.
2. **정답과 각 오답의 차이 = 실질적 개념 차이 하나**:
   (a) 순서(지금 먼저 할 일 vs 그다음 일) (b) 주체·역할(감사인 vs 경영진, 소유자 vs 관리자) (c) 통제 유형(예방 vs 탐지·교정, 자동 vs 수동)
   (d) 수준·범위(근본 원인·프로세스 vs 개별 건, 전사 vs 국지) (e) 목적 vs 부수 효과 (f) 유사 개념 혼동(RPO vs RTO, 속성 vs 변수 샘플링, IDS vs IPS, SOC 1 vs SOC 2 …)
3. **말장난 금지**: 보기 간 우열이 단어 뉘앙스·수식어 하나(‘충분히’, ‘적절히’, ‘공식적으로’)·부정 표현·문장 길이·구체성 차이로 갈리면 안 된다. 정답의 근거는 해설에서 **ISACA 원칙 또는 개념 한 가지로 명확히** 설명돼야 한다. CISA 전문가 두 명이 다른 답을 낼 여지가 있으면 다시 쓴다.
4. **허수 오답 금지**: 비용·서식·일정·인력 사기·문서 양식 같은 지엽 이슈, 명백한 비윤리·불법·극단 행동(징계, 전면 즉시 중단, 모든 데이터 삭제), ‘아무것도 하지 않음’류는 오답으로 쓰지 않는다.
5. **보기 균형**: 4개 보기 길이 차이 ±20% 이내, 같은 문법 구조. 정답이 가장 긴 보기인 비율은 배치당 30% 이하. ‘위험·평가·보고·정렬’ 같은 ISACA 단골어를 정답에만 몰아주지 말고 오답도 감사·통제 언어로 쓴다.
6. **지문**: 결함의 결과나 정답을 지문이 미리 설명하지 않는다(결과 추론이 문제의 일부). 짧은 지문(1~2문장, 80자 내외) 약 35% + 사례형 약 65%.
   ‘IS 감사인이’로 시작하는 지문은 배치당 20% 이하 — 주체(감사 책임자, 감사위원회, 외부 감사인, CIO, CISO, 위험관리자, 프로젝트 관리자)와 질문 형식을 다양하게.
7. **키워드**: FIRST · BEST · PRIMARY · GREATEST · MOST만 사용. LEAST·NOT·EXCEPT 금지. 키워드 없는 일반형(NONE)은 배치당 3문항 이하.
8. **해설**: 정답 해설은 *결정적 차이*를 밝힌다(예: “다른 보기도 유효한 통제지만 이 상황의 핵심은 X이므로 Y가 우선”). 오답 해설은 *그 보기가 정답이 되는 상황*을 함께 쓴다.
9. **고난도 비중**: 4개 보기가 모두 맞는 말이고 순서·우선순위로만 갈리는 문항을 25% 이상.
10. 검사: `node tools/check-staging.mjs --quality <파일들>` — 형식 검사 + 실전 품질 기준(패턴 찍기 정답률 ≤33%, 최장·최단 보기=정답 각 ≤32%, 허수 오답 0, 부정형 0, ‘IS 감사인이’ 시작 ≤25%)을 모두 통과해야 한다.

## 0-A. 공식 형식 정렬 v3 — 0장과 함께 적용 (충돌 시 이 장 우선)

근거: ISACA 공식 QAE 샘플(구판 매뉴얼 150문항 + 현행 PERFORM 문항)의 형식 분석. **공식 문항 문장은 저작물이므로 절대 옮기지 않는다** — 아래는 형식 특징만 요약한 것이다.

1. **감사인 관점 약 40%**: 공식 문항의 약 40%는 감사인이 판단 주체다. 질문 형태는 다음과 같다.
   - "감사인이 가장 먼저 해야 할 일은?" / "감사인이 권고할 가장 적절한 통제는?" / "감사인의 가장 큰 우려는?"
   - "감사인이 내려야 할 결론은?" / "감사인이 검토해야 할 것은?" / "가장 신뢰할 수 있는 감사 증거는?"
   - 문장 앞머리는 다양하게 쓴다: "~를 검토하던 감사인이 …", "감사 계획 단계에서 IS 감사인의 주된 목표는?", "~ 감사 중 … 이 발견되었다. 감사인은?".
2. **감사인 역할 함정(감사인 관점 문항의 핵심)**: 감사인은 *직접 고치거나 차단·구현하지 않는다*. 감사인의 행동은 이해·평가·검증·보고·권고다.
   - 오답에는 그럴듯한 *실무자 조치*를 넣는다: 직접 차단·수정·권한 회수·절차서 작성 등. 이런 보기는 "감사인의 역할을 넘는 행동"이어서 틀린 것이다.
   - 감사인 행동끼리도 순서로 갈린다: 사실 확인·영향 평가 → 보고 → 권고.
   - 정답이 늘 "평가한다"가 되지 않게 한다. 영향 평가, 보고, 권고, 추가 테스트 등 상황에 맞는 감사 행동이 고르게 정답이 되어야 한다. 그래야 패턴 찍기 정답률이 오르지 않는다.
3. **짧은 지식·정의형 약 35%**: 공식 문항의 상당수는 한 줄짜리 개념 문항이다.
   - 예: "X의 주된 목적은?", "Y에 가장 적합한 샘플링 방법은?", "Z를 가장 잘 막는 통제는?", "W가 침해하는 트랜잭션 속성은?"
   - 지문은 80자 이하 한 문장이다. 상황 장식을 붙이지 않는다.
   - 보기는 짧은 명사구여도 된다. 예: "속성 샘플링 / 변수 샘플링 / 층화 평균 / 차이 추정".
4. **ISACA 고유 관점 문항**: 상식·실무 감각과 다르게 *ISACA 공식 교재(CRM·QAE)의 확립된 입장*으로 정답이 정해지는 문항이다. 해당 문항에는 `"p": 1`을 넣는다.
   - 확신하는 입장만 쓴다. 추측으로 "ISACA는 이렇게 본다"를 만들지 않는다. 확립된 입장의 예:
     - 데이터 분류의 가장 큰 이점은 **통제 비용의 적정화**(과잉 보호 방지)다.
     - 위험 수용 결정은 **경영진(위험 소유자)** 몫이다.
     - 감사인은 위험이 낮고 보완 통제가 있으면 **지적하지 않을 수 있다**.
     - DRP 준비 상태의 최선의 증거는 **테스트 결과**다.
     - 정보보안 정책 승인 주체는 **이사회·최고경영진**이다.
     - 위험 기반 계획의 첫 단계는 **자산·프로세스 식별**이다.
     - 가장 신뢰할 수 있는 증거는 **독립 제3자로부터 직접 받은 확인서**다.
     - 운영 효과성 테스트는 **준거성 테스트**로 한다.
     - IT 운영위원회(Steering Committee)는 **IT 계획·예산 승인과 진척 감시**를 맡는다.
   - 해설 정답 문장에 "ISACA 관점:" 으로 시작하는 근거 문장을 넣고, 왜 상식적 보기가 아닌지를 밝힌다.
5. 0장 6번의 "'IS 감사인이' 시작 ≤20%" 규칙은 *문장 앞머리* 다양화 규칙이다. 감사인 관점 자체를 줄이라는 뜻이 아니다.

## 1. 출력 형식 (JSON)

- 파일 = **JSON 배열** (UTF-8). 주석·후행 쉼표 금지. 백슬래시(\) 사용 금지.
- 문자열 안에 따옴표가 필요하면 **반드시 ‘ ’ 또는 “ ” 또는 「 」** 를 쓴다. (ASCII 큰따옴표 `"` 를 문자열 내부에 쓰면 JSON이 깨진다.)
- 문항 1개 = 한 줄 객체(가독성 위해 문항마다 줄바꿈):

```
{"t":"샘플링","k":"BEST","lv":2,"q":"지문","o":["보기1","보기2","보기3","보기4"],"a":2,"e":["보기1 해설","보기2 해설","보기3 해설","보기4 해설"],"f":"ISACA 한 줄 공식"}
```

| 키 | 의미 | 규칙 |
|---|---|---|
| t | 토픽 태그 | 배정받은 태그 문자열을 **글자 그대로** 사용 |
| k | 결정 키워드 | `FIRST` `BEST` `PRIMARY` `GREATEST` `MOST` `NONE` 중 하나 (LEAST 금지) |
| lv | 난이도 | 1 기본 · 2 실전 · 3 고난도 |
| q | 지문 | 아래 2장 |
| o | 보기 4개 | 아래 3장 |
| a | 정답 인덱스 | 0~3 (0 기준) |
| e | 보기별 해설 4개 | `o`와 **같은 순서**로 1:1 대응. 아래 4장 |
| f | ISACA 한 줄 공식 | 아래 5장 |
| p | (선택) ISACA 고유 관점 | 0-A장 4번에 해당하면 `1`, 아니면 키 생략 |

## 2. 지문(q)

- 실제 CISA 시험(한국어 번역판) 수준의 자연스러운 한국어. **70% 이상 상황(시나리오)형**:
  `IS 감사인이 ~을 검토하던 중 ~을 발견하였다. 감사인이 가장 먼저(FIRST) 해야 할 일은?`
  나머지는 개념 적용형. 단순 정의 암기형은 15% 이하.
- 결정 키워드는 **한국어 + 괄호 속 영문 대문자**로 반드시 표기한다(앱이 자동 컬러 뱃지 처리):
  - FIRST → `가장 먼저(FIRST)`, `최우선으로(FIRST)`
  - BEST → `가장 적절한(BEST)`, `가장 효과적인(BEST)`, `가장 좋은(BEST)`
  - PRIMARY → `주된(PRIMARY)`, `주요(PRIMARY)`
  - GREATEST → `가장 큰 우려(GREATEST concern)`, `가장 큰 위험(GREATEST risk)`, `가장 큰 영향(GREATEST impact)`
  - MOST → `가장 중요한(MOST important)`, `가장 가능성이 높은(MOST likely)`, `가장 효과적으로(MOST effectively)`, `가장 신뢰할 수 있는(MOST reliable)`
  - LEAST → `가장 적은(LEAST)`, `가장 낮은(LEAST)` / NONE → 키워드 없음
- 80문항 배치 기준 키워드 분포(대략): BEST 20 · MOST 16 · FIRST 15 · PRIMARY 13 · GREATEST 12 · LEAST+NONE ≤ 4
- 난이도 분포: lv1 25% · lv2 50% · lv3 25%
- 산업·조직을 다양하게(은행, 보험, 증권, 병원, 제조, 유통/전자상거래, 공공기관, 통신, 물류, 스타트업, 글로벌 기업, 대학).
  같은 배치 안에서 같은 논점·같은 상황을 반복하지 않는다.
- ISACA 공식 문제(QAE)·시중 교재 문장을 옮기지 말고 **창작**한다.

## 3. 보기(o)

- 정확히 4개. ISACA 관점에서 **최선의 답이 단 하나로 명확**해야 한다(논쟁적 문항 금지).
- 오답은 실제 수험생이 고르는 **그럴듯한 함정**으로 만든다:
  순서 오류(위험평가 전에 해결책), 역할 혼동(감사인이 직접 구현·승인·수정), 탐지 vs 예방, 증상 vs 근본원인,
  범위가 너무 좁거나 넓음, 비용 대비 효과 부적절, 기술적으로는 맞지만 비즈니스 목표와 무관, 경영진 책임을 감사인이 대신함.
- 4개 보기의 길이·문체·문법 구조를 비슷하게. **정답이 가장 길거나 가장 구체적이 되지 않도록** 주의.
- `모두 정답` `정답 없음` `위의 모든 것` 금지. 보기끼리 의미 중복·포함 관계 금지.
- 정답 위치(a)를 0~3에 고르게 분산한다(빌드 시 재배치되지만 편중 금지).

## 4. 해설(e) — 앱의 핵심 가치

- **정답 보기 해설(70~180자)**: 적용되는 ISACA 원칙 + 왜 다른 보기보다 ‘최선’인지.
- **오답 보기 해설(50~150자)**: 어떤 함정인지 + 어떤 상황이라면 맞거나 언제 하는 일인지.
- `정답:` `오답:` 같은 접두어 금지(앱이 라벨을 붙인다).
- `A`, `1번`, `①`, `위 보기`처럼 **보기 위치를 지칭하지 말 것**(보기는 섞여서 출제된다). 내용으로 지칭한다.
- 사실 오류 금지. 확실하지 않은 수치·연도·법조문 번호는 쓰지 않는다.

## 5. ISACA 한 줄 공식(f)

- 이 문항의 판단 원리를 **15~45자**의 외우기 쉬운 공식으로. `→` `>` `=` `≠` `✕` 활용.
  - `FIRST = 이해·위험평가 → 그다음 통제·해결책`
  - `감사인 = 식별·보고·권고 (직접 구현 ✕)`
  - `증거 신뢰도: 외부·독립 > 내부, 문서 > 구두`
  - `접근 승인 = 데이터 소유자, 구현 = 보안관리자`

## 6. ISACA 사고방식 (정답 판단 기준 — 일관 적용)

1. **위험 기반**: 먼저 이해하고 위험을 식별·평가해 우선순위를 정한다.
2. **비즈니스 정렬**: IT·보안·감사는 비즈니스 목표·전략을 지원해야 한다.
3. **감사인의 역할**: 식별·평가·보고·권고. 직접 수정·구현·운영·승인하지 않는다.
4. **독립성·객관성**: 자신이 설계·구현·운영한 업무를 감사하지 않는다. 침해 시 공개(disclose)한다.
5. **경영진 책임**: 위험 수용·통제 구현·자원 배분은 경영진(최종 책임은 이사회). 감사인은 수용된 위험이 위험성향을 넘으면 상위(고위 경영진·감사위원회)에 보고한다.
6. **예방 > 탐지 > 교정**, **자동 > 수동** (단, 비용 대비 효과 고려).
7. **근본 원인 > 증상**, 프로세스·정책 개선 > 일회성 수정.
8. **정책 우선(하향식)**: 정책 → 표준 → 절차 → 지침. 정책이 없으면 정책부터.
9. **증거 기반**: 충분·적절한 증거. 외부 독립 > 내부, 감사인이 직접 수집 > 간접, 문서 > 구두, 원본 > 사본.
10. **인명 안전 최우선**: 재해·비상 시 사람의 안전이 데이터·시스템보다 먼저.

보조 규칙: 데이터 소유자가 분류·접근 승인, 관리자(custodian)가 구현 · SoD 불가 시 보완통제(감독·검토·로그 모니터링) ·
모든 변경은 승인-테스트-문서화(긴급 변경도 사후 승인) · 아웃소싱해도 책임(accountability)은 이전 불가 ·
감사 발견사항은 경영진과 사실 확인 후 보고(감사인이 임의 삭제 ✕) · 사기 조사는 감사인의 책임이 아니며 징후는 적절한 권한자에게 보고.

## 7. 핵심 사실 시트 (일관성 유지 — 아래와 모순 금지)

**D1 감사 프로세스**
- 감사 헌장 = 감사 기능의 목적·권한·책임, 이사회/감사위원회 승인. 참여서(engagement letter) = 개별 감사 건의 범위·책임.
- IS 감사 기능은 감사위원회에 기능적으로 보고할 때 독립성이 가장 높다.
- 감사위험 = 고유위험 × 통제위험 × 적발위험. 감사인이 직접 조정 가능한 것은 **적발위험**뿐. 통제위험↑ → 실증 테스트 확대.
- 준거성(compliance) 테스트 = 통제가 설계대로 운영되는지 → **속성 샘플링**. 실증(substantive) 테스트 = 거래·잔액의 정확성·완전성 → **변수 샘플링**.
- 발견 샘플링 = 희귀 사건(사기)을 1건이라도 찾을 목적. 정지-진행 = 오류가 거의 없을 것으로 예상될 때 표본 최소화. 층화 = 변동성 큰 모집단을 그룹화(고액 항목 전수 등).
- 표본 크기: 신뢰수준↑·예상오류율↑·모집단 변동성↑ → 표본↑ / 허용오류(정밀도 범위)↑ → 표본↓.
- CAATs: GAS = 대량 데이터 추출·분석·전수 검사 · 테스트 데이터 = 프로그램 로직 검증(가상 거래) · ITF = 운영 시스템에 가상 엔티티로 테스트(테스트 거래 제거 필요) · 병행 시뮬레이션 = 감사인 프로그램으로 실데이터 재처리·비교 · SCARF/EAM = 내장 모듈로 기준 초과 거래 수집 · 스냅샷 = 처리 경로 지점별 데이터 캡처 · 감사 훅 = 의심 거래 실시간 플래그(조기 탐지) · CIS = DBMS 환경에서 조건 충족 거래 시뮬레이션.
- CAAT 사용 시: 데이터 무결성·완전성 확인, 원본이 아닌 사본 사용, 감사인이 직접 통제.
- 증거 신뢰성 요인: 제공자의 독립성, 제공자 자격, 객관성, 적시성. 감사인이 직접 관찰·재수행한 증거가 가장 강함.
- 발견사항 구성 = 조건·기준·원인·영향(+권고). 종료 회의(exit interview)에서 사실 확인·경영진 응답 확보 후 최종 보고.
- CSA = 업무 부서가 통제를 스스로 평가, 감사인은 촉진자. 감사 기능을 대체하지 않는다.
- 범위 제한은 보고서에 명시하고 감사위원회에 보고.

**D2 거버넌스·관리**
- 이사회 = IT 거버넌스 최종 책임. IT 전략위원회 = 이사회 수준(전략 자문). IT 운영위원회(steering committee) = 경영진 수준(프로젝트 우선순위·자원·진척).
- 거버넌스 = EDM(평가·지시·모니터링, 이사회) / 관리 = APO·BAI·DSS·MEA(Plan-Build-Run-Monitor, 경영진).
- COBIT 2019: 40개 목표·5개 도메인, 거버넌스 시스템 6원칙, 프레임워크 3원칙, 7개 구성요소, 설계요소, 역량 수준 0~5, 목표 캐스케이드(이해관계자 동인→기업 목표→정렬 목표→거버넌스·관리 목표).
- BSC 4관점 = 재무·고객·내부 프로세스·학습과 성장.
- ALE = SLE × ARO, SLE = 자산가치 × 노출계수(EF). 위험 대응 = 회피·완화·전가(공유)·수용. 위험 수용 주체 = 경영진(위험 소유자).
- KGI = 목표 달성 결과(후행), KPI = 성과 동인(선행), KRI = 위험 조기 경고.
- QA = 프로세스·표준 준수 보증(독립적), QC = 산출물 검사. CMMI 1 초기 · 2 관리 · 3 정의 · 4 정량적 관리 · 5 최적화.
- SoD 핵심 금지 조합: 개발 ↔ 운영 환경 이관/운영, 보안관리 ↔ 시스템 운영/개발, DBA ↔ 응용 개발, 거래 승인 ↔ 기록 ↔ 자산 보관, 변경 요청 ↔ 승인 ↔ 이관.
- 강제 휴가·직무 순환 = 사기 탐지(탐지 통제). 퇴사 시 접근 권한 즉시 회수. 채용 전 배경 조사.
- 아웃소싱 계약 필수: 감사권(right to audit), SLA, 기밀유지, 데이터 소유권·반환·삭제, 종료 조항, BCP 요건. SOC 1 = 재무보고 통제, SOC 2 = 보안·가용성 등, Type II = 일정 기간 운영 효과성(Type I = 특정 시점 설계).
- 소스코드 에스크로 = 벤더 파산·지원 중단 대비.

**D3 취득·개발·구현**
- 비즈니스 케이스 = 타당성 분석 기반, 프로젝트 전 주기에 걸쳐 갱신·재검증. 프로젝트 스폰서 = 자금·최종 성공 책임. UAT 승인 = 사용자(업무 부서).
- PERT 기대시간 = (낙관 + 4×최빈 + 비관) ÷ 6. 크리티컬 패스 = 가장 긴 경로(여유시간 0). CPI = EV/AC, SPI = EV/PV (1 미만 = 비용 초과·일정 지연).
- FPA = 기능 기반 규모 추정(언어 독립). 타임박스 = 기간·자원 고정, 범위 조정(범위 크리프 방지).
- Scrum: 제품 책임자 = 백로그 우선순위, 스크럼 마스터 = 촉진·장애 제거(관리자 아님). Agile 위험 = 문서화·통제 증거 부족. DevOps = SoD 약화 → 자동화 통제(파이프라인 승인·코드 리뷰·로그)로 보완. DevSecOps = 보안 시프트 레프트(SAST/DAST/SCA 자동화).
- 입력 통제: 체크 디지트(전치·전사 오류), 범위·한계·유효성·존재·합리성·완전성·중복·논리관계·순서 검사, 키 검증. 배치 통제: 금액 합계·항목 수·문서 수·해시 합계. 런투런 합계 = 처리 단계 간 무결성.
- 테스트: 단위 → 통합(하향식 = 스텁, 상향식 = 드라이버) → 시스템 → 인수(UAT). 회귀 = 변경 후 기존 기능 유지 확인. 사회성 = 기존 환경 내 공존. 병행 = 신·구 결과 비교.
- 전환: 병행(가장 안전·고비용) · 단계적 · 파일럿 · 직접/빅뱅(가장 위험, 폴백 계획 필수). 데이터 변환 = 레코드 수·통제 합계 조정, 사용자 승인.
- PIR = 구현 후 일정 기간 경과 뒤 편익 실현·교훈 평가.

**D4 운영·복원력**
- 인시던트 관리 = 신속한 서비스 복구 / 문제 관리 = 근본 원인 제거.
- 무단 변경 탐지 = 운영 코드와 승인 버전 비교. 개발자는 운영 환경 접근 금지. 긴급 변경도 사후 승인·문서화.
- RAID 0 = 스트라이핑(중복 없음) · 1 = 미러링 · 5 = 분산 패리티(1개 장애 허용) · 6 = 이중 패리티(2개) · 10 = 미러+스트라이프.
- SLA = 제공자↔고객, OLA = 내부 부서 간, UC = 외부 공급자 지원 계약.
- DB: 참조 무결성 = 외래키는 존재하는 기본키만 참조, 엔터티 무결성 = 기본키 NULL 불가, 반정규화 = 성능↑·무결성 위험↑, 2단계 커밋 = 분산 트랜잭션 원자성, DBA 활동은 로그·독립 검토.
- BIA = 중요 프로세스·중단 영향·RTO/RPO 결정(프로세스 소유자 인터뷰, 고위 경영진 승인). BCP 수립 첫 단계 = BIA(위험평가 포함).
- RTO = 복구 목표 시간, RPO = 허용 데이터 손실 시점(→ 백업 주기), MTD(MAO) = 최대 허용 중단, WRT = 시스템 복구 후 업무 재개까지. **RTO + WRT ≤ MTD**. SDO = 대체 모드 서비스 수준. RTO·RPO가 짧을수록 비용↑.
- DR 사이트: 미러(즉시) < 핫(수 시간) < 웜(수 일) < 콜드(수 주) — 비용은 역순. 상호 협정 = 저비용이나 호환성·가용성·강제력 위험. 대체 사이트는 동일 재해 영향권 밖.
- 백업: 전체(복원 최속), 증분(백업 최속, 복원 = 전체 + **모든** 증분), 차등(복원 = 전체 + **마지막** 차등). 백업 유효성의 최선 증거 = 정기 복원 테스트. 전자 볼팅 = 배치 원격 전송, 원격 저널링 = 트랜잭션 로그 실시간 전송.
- BCP 테스트 강도: 체크리스트 < 구조적 워크스루(탁상) < 시뮬레이션 < 병행 < 전면 중단(가장 위험). 다양화 라우팅 = 동일 케이블 경로 분리, 대체 라우팅 = 다른 매체·경로.

**D5 정보자산 보호**
- 정보보안 정책 = 고위 경영진 승인·전 직원 전파·정기 검토. 사회공학 대응의 최선 = 보안 인식 교육.
- 맨트랩 = 피기백킹/테일게이팅 방지. 화재: 습식(누수 위험) · 건식(동결 지역) · 프리액션(데이터센터 권장 물 방식) · 청정 가스(FM-200 등, 장비 보호) · CO2(무인 구역만). 블랙아웃 = UPS+발전기.
- 접근 승인 = 데이터 소유자, 최소 권한, 정기 접근 재인증, 공유 계정 금지(책임추적성), PAM(특권 세션 기록·체크아웃).
- DAC = 소유자 재량, MAC = 보안 레이블 강제, RBAC = 역할, ABAC = 속성.
- MFA = 서로 다른 **유형** 2개 이상(비밀번호+PIN은 MFA ✕).
- 생체인식: FAR(타인 수락) = 보안상 가장 치명적, FRR(본인 거부) = 불편, CER(EER) = FAR=FRR 지점, 낮을수록 정확. 민감도↑ → FAR↓·FRR↑.
- SSO = 편의↑ vs 단일 실패점 → 강력 인증 필요. Kerberos = KDC·티켓·대칭키·시간 동기화.
- OSI: L7 응용(WAF·프록시·응용 게이트웨이) · L6 표현 · L5 세션 · L4 전송(TCP/UDP·포트) · L3 네트워크(IP·라우터·패킷 필터·IPsec) · L2 데이터링크(MAC·스위치·ARP 스푸핑·VLAN) · L1 물리(허브·리피터).
- 방화벽: 패킷 필터(L3/L4, 빠르나 약함) < 상태 검사 < 애플리케이션 프록시(L7, 가장 강력·느림). 구성: 스크린드 서브넷(DMZ) = 가장 안전. 규칙 = 기본 거부(default deny), 구체적 규칙 우선.
- IDS = 탐지·경보(수동), IPS = 인라인 차단(능동, 오탐 시 정상 차단 위험). 시그니처 = 알려진 공격(제로데이 ✕), 이상(통계) = 신종 탐지·오탐 많음.
- 제로 트러스트 = 위치 기반 암묵적 신뢰 제거, 모든 요청 인증·인가, 최소 권한, 마이크로세그멘테이션, 지속 검증.
- DLP의 선행 조건 = 데이터 분류.
- 대칭키 = 빠름·키 배포 문제, 비대칭 = 키 교환·서명, 디지털 봉투 = 대칭키를 수신자 공개키로 암호화. 해시 = 무결성, HMAC = 무결성+인증(부인방지 ✕).
- **전자서명 = 송신자 개인키로 해시 서명 → 송신자 공개키로 검증** (무결성·인증·부인방지, 기밀성 ✕). **기밀성 = 수신자 공개키로 암호화 → 수신자 개인키로 복호화.**
- CA = 인증서 발급·서명, RA = 신원 확인, CRL = 폐기 목록, OCSP = 실시간 상태 확인, CPS = 인증 실무 준칙. 서명용 개인키는 에스크로하지 않는다(부인방지 훼손).
- 클라우드 책임: IaaS(고객 = OS·앱·데이터) → PaaS(앱·데이터) → SaaS(데이터·접근). 데이터 보호 책임은 항상 고객. CASB = 클라우드 사용 가시성·정책.
- 가상화 = 하이퍼바이저 보안 최우선(침해 시 전체 VM). 무선 = WEP 금지, WPA2/3-Enterprise(802.1X) 권장, SSID 숨김·MAC 필터 = 약한 통제.
- SQLi → 파라미터화 쿼리·입력 검증 · XSS → 출력 인코딩·CSP · CSRF → 요청별 토큰·SameSite 쿠키.
- 취약점 스캔 = 알려진 취약점 식별 / 침투 테스트 = 실제 악용 검증(사전 서면 승인·범위 합의 필수). 더블 블라인드 = 방어팀도 모름(대응 능력 측정).
- 사고 대응: 준비 → 탐지·분석 → 봉쇄 → 근절 → 복구 → 교훈. 랜섬웨어 감염 첫 조치 = 격리(봉쇄).
- 포렌식: 증거 보관 연속성(chain of custody), 원본 보존·비트스트림 이미지·해시 검증, 휘발성 높은 것(메모리)부터 수집.

## 9. 작업 절차 (작성 에이전트용)

1. 배정된 배치 ID·토픽 태그·문항 수를 확인한다. 태그별 문항 수를 정확히 맞춘다.
2. **파트1(40문항)** → `staging/<배치ID>_p1.json`, **파트2(40문항)** → `staging/<배치ID>_p2.json` 을 Write 도구로 작성한다.
   생각 단계에서 문항을 미리 길게 초안하지 말고, 간단히 계획한 뒤 바로 파일에 작성한다.
3. 파트2 작성과 **같은 응답에서** 검사기를 실행한다:
   `node /home/user/cisa/tools/check-staging.mjs /home/user/cisa/staging/<배치ID>_p1.json /home/user/cisa/staging/<배치ID>_p2.json`
4. ERROR가 있으면 수정 후 재검사. WARN 중 ‘해설 정렬 의심’ ‘보기 위치 지칭’은 반드시 고친다.
5. **최종 응답은 한 줄만**: `<배치ID> OK <문항수>` (다른 설명 금지).
6. git 명령 금지. 배정된 staging 파일 외 다른 파일 생성·수정 금지.

## 10. 신규 문제 팩 추가 방법 (유지보수자용)

1. 위 형식으로 `staging/<팩이름>_D<도메인번호>_*.json` 작성 (파일명에 `D1`~`D5` 포함 → 도메인 자동 인식).
2. `node tools/check-staging.mjs staging/<파일>.json` 으로 검사.
3. `node tools/build-questions.mjs` 실행 → 기존 문항 ID를 보존하고, 신규 문항에 다음 번호 ID 부여, 중복 제거, 정답 위치 균형화 후 `data/questions/d1~d5.js` 갱신.

## 11. 기존 문항 개정(v2) 절차 (개정 에이전트용)

1. 입력 파일(80문항, `id` 포함)을 Read 한다. 각 문항을 0장 기준으로 다시 쓴다.
   - `id`·`d`·`t`와 *시험하는 개념(학습 목표)* 은 유지한다. 지문·보기·정답 문구·해설·공식은 모두 고쳐도 된다.
   - 부정형(LEAST)은 같은 개념을 묻는 FIRST·BEST·PRIMARY·GREATEST·MOST 문항으로 바꾼다.
2. 출력 스키마 = 1장 스키마 + 맨 앞 `"id"`. 앞 40문항 → `<OUT>_p1.json`, 뒤 40문항 → `<OUT>_p2.json`.
3. 두 파일 작성 후 같은 응답에서 `node /home/user/cisa/tools/check-staging.mjs --quality <p1> <p2>` 실행 → ERROR 0이 될 때까지 해당 문항을 고친다.
4. 최종 응답 한 줄: `<배치ID> OK 80`.
